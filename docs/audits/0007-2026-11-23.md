## Findings

F1 to F5 are about what the tool should do. Each needs the owner's choice; none should be settled by aligning one text to the other.

### F1. `contradiction`: a foreign file in the cache is "never replaced" in one place and replaceable in another
- R47, `docs/design.md:309-311`: "The tool replaces only the files with the fixed names it creates there, never another file found in that folder." A file that the tool did not create, but that carries one of the fixed names, may be replaced under this rule.
- R34, `docs/design.md:250-251`: "a file in the cache folder that the tool did not create is never replaced". `.claude/agents/fable-reviewer.md:36` says the same ("replaces a file in the cache that the tool did not create").
- The two rules give different answers for a foreign file with a fixed name. No R34 case names it. Also open: the names of cached CRL files, which must not come from the input if R47 is to hold.
- Change: the owner decides which rule holds; then R47, R34 and the reviewer prompt say the same, and R34 gets the case. Item 4 and 13 of the review of 20a420d on PR #3.

### F2. `contradiction`: R47 sends the reader to R42 for the cache folder, and the test rule does not fit the candidate crate on Windows
- R47, `docs/design.md:307-309`: "The cache folder is the operating system's standard one (R42) ... Tests move it only through the system's own variables (`HOME`, `XDG_CACHE_HOME`, `LOCALAPPDATA`)."
- R42, `docs/design.md:410-415`: the Windows item names registry keys and the uninstall entry only. It names no cache folder and no folder for the manifest. macOS and Linux have both (`docs/design.md:416-419`).
- The architecture table names `directories` as the candidate crate for the cache (`docs/design.md:440`). On Windows that crate does not read `LOCALAPPDATA`: it asks the system (`SHGetKnownFolderPath`). Checked in the crate sources: `dirs-sys` `src/lib.rs:153,180` (`known_folder_local_app_data`), used by `directories` `src/win.rs:13`. A test that sets `LOCALAPPDATA` would still reach the user's real cache, which R34 forbids (`docs/design.md:249-250`).
- The manifest of R41 lives in the config folder. No rule says how tests of `install-menu` move that folder.
- Change: name the Windows cache and config folders in R42; decide before roadmap 3.5 how the folder is found on Windows so that the test rule of R47 can work. `directories` is not a dependency yet (`Cargo.toml:16`), so nothing is broken today. Item 5 of the review of 20a420d.

### F3. `contradiction`: the "create new" rule has three different scopes
- R31, `docs/design.md:202-203`, and `CLAUDE.md:160-161`: "every file `check` and `extract` write outside the cache".
- `.claude/agents/fable-reviewer.md:35-36`: "opens any file for writing outside the tool's cache (the report too) without `create_new`", for every command.
- `README.md:69-71`: "Nothing is ever overwritten, not even an earlier report. Every file is created with an exclusive "create new" operation".
- The commit message of 20a420d says the rule was "scoped to check and extract, so the install manifest (R41) is not caught by it". The README and the reviewer prompt were not scoped. With the narrow scope, no rule says what `install-menu` does when it meets a foreign menu item with the same name, which `uninstall` could then remove (R41, `docs/design.md:404-408`).
- Change: the owner decides the rule for `install-menu`; then the three texts carry one scope. Items 1 to 3 of the review of 20a420d.

### F4. `contradiction` (gap): `--no-report` and the second report
